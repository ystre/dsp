[[deployment]]
= Deployment

== Charts

[source,subs="attributes+"]
----
deploy/helm/
  server/    {project}-server    the service: workload, Services, monitoring resources, dashboard, helm test
  loadgen/   {project}-loadgen   one load generator run as an Indexed Job
  kafka/     {project}-kafka     a KRaft Kafka cluster (Strimzi custom resources): shared or dedicated
  umbrella/  {project}           integration chart: server, Kafka topics, dedicated kafka, loadgen
  deps/      {project}-deps      the platform, once per cluster: kube-prometheus-stack, Strimzi, shared Kafka
----

The directories are named after roles. The chart names carry the project name
and are rewritten by `tools/rename.sh`. In the umbrella chart, the subcharts are
aliased to role keys (`server`, `kafka`, `loadgen`), so values files do not
depend on the project name either.

[[deployment-scopes]]
Two scopes are kept apart:

* *Per release* (the umbrella chart): everything a deployment owns, including
  its Kafka topics. One release per namespace; the lab and the CI deploy test
  use different namespaces, so their metrics (the `namespace` label, the
  dashboard's namespace selector) and benchmark results never mix, and their
  topics carry the namespace as a prefix (<<deployment-topics>>).
* *Per cluster* (the dependencies chart, <<deployment-deps>>): operators, the
  shared observability stack and the shared Kafka cluster. CRDs are
  cluster-wide and owned by exactly one Helm release, so this is installed
  once and never by a release.

Resource names are `<release>-server` and `<release>-loadgen`. Inside one
umbrella release, the load generator therefore finds the server at
`<release>-server:7200` without configuration.

All charts have a `values.schema.json`, so mistyped or unknown values fail at
install time. Their versions equal `VERSION` (`tools/sync-version.sh`).

[source,sh,subs="attributes+"]
----
deploy/lab/platform.sh                              # once per cluster: the platform (below)
helm dependency update deploy/helm/umbrella
helm install {project} deploy/helm/umbrella -n {project} --create-namespace
helm test {project} -n {project}
----

[[deployment-tuning]]
== Performance tuning on Kubernetes

[cols="2,5",options="header"]
|===
| Setting | Effect and requirements
| `performance.guaranteedQoS: true` with integer `resources.requests.cpu` | Requests equal limits: Guaranteed QoS. With the kubelet's static CPU manager policy (`--cpu-manager-policy=static`), the containers get exclusive CPUs, and the server runs one reactor per CPU in its affinity mask. The topology manager (`single-numa-node`) keeps them on one NUMA node.
| No CPU limit (default) | Without Guaranteed QoS, a CPU limit means CFS throttling: periodic stalls of up to the CFS period, which show as latency spikes. The dashboard plots throttled time.
| `performance.hostNetwork: true` | The server binds on the node's interfaces: no veth, bridge or NAT on the path. One pod per node and port. Use it for capacity measurements.
| `performance.sysctls` | Namespaced sysctls. `net.ipv4.ip_local_port_range` is "safe"; `net.core.somaxconn` and `net.ipv4.tcp_*` buffers need the kubelet's `--allowed-unsafe-sysctls`.
| `performance.hugepages2Mi` | Requests 2 MiB huge pages (the node must have them reserved) and mounts them for the buffer pools.
| `performance.runtimeClassName`, `priorityClassName` | E.g. a runtime class with a seccomp profile that allows io_uring (<<arch-security>>); priority over batch workloads.
| `topologySpreadConstraints`, `affinity` | One server per node, away from the load generators.
| Node level (outside the chart) | NIC RSS queues and IRQ affinity aligned with the CPUs given to the pod; `irqbalance` off on benchmark nodes; the governor and the other host settings of <<bench-host>>.
|===

[[deployment-loadgen]]
== Load generator chart

One release is one run: an Indexed Job with `instances` pods, each running the
generator with `--instance <index>` and the flags in `run` (keys equal the
contract's CLI flags, <<loadgen-cli>>). The pods serve `loadgen_*` metrics
(PodMonitor) and linger `metrics.linger` seconds after the run for the final
scrape. `target` defaults to `<release>-server:7200`. `tools/bench/run.py
--target k8s` installs it once per repeat and reads the summary from the pod log.

Its image is `<image.registry>/<image.repository>:<image.tag>`, by default
`oci-registry.internal.ystre.org:5000/{project}-loadgen:<appVersion>` (`global.image.*` overrides).
`placement.dedicatedNodes=true` (`run.py --loadgen-nodes`) confines the pods to
the load generator nodes (<<deployment-nodes>>); without it they run on any
node. `nodeSelector`, `tolerations` and `affinity` add to that.

[[deployment-topics]]
== Kafka: shared cluster and topics

The platform runs one shared Kafka cluster (`kafka` in namespace `platform`,
bootstrap `kafka-kafka-bootstrap.platform.svc:9092`). A release does not own a
cluster; it owns *topics* on it, listed in the umbrella chart's `topics.items`.

* Each topic is a Strimzi `KafkaTopic` in the cluster's namespace (the topic
  operator watches only there), named `<prefix><name>`. The prefix defaults to
  `<release namespace>.`: `{project}.data` for the lab, and
  `{project}-ci.<run id>.data` for the CI deploy test, so lab and CI topics,
  and the topics of different CI runs, never mix.
* Labels: `owner-namespace` (the release namespace), `app.kubernetes.io/instance`
  (the release), plus `topics.labels` (CI adds `ci-run=<run id>`).
* Topics outlive the release (`helm.sh/resource-policy: keep`): uninstalling or
  reinstalling keeps their data. `deploy/lab/down.sh --delete-topics` deletes
  the topics of the release's current revision as well.
* The CI deploy test deletes its topics after a successful run only. After a
  failure they are kept for inspection, and later runs list them as a warning
  (<<ci>>). Nothing deletes them automatically:
  `kubectl delete kafkatopic -n platform -l ci-run=<run id>` does.
  Alternatively, `kubectl delete kafkatopic -n platform -l owner-namespace={project}-ci`
  deletes all CI created topics.

Isolation is by name, not by resources: the lab and a concurrent CI run share
the brokers. For benchmarks of a Kafka sink without neighbours, a release can
have a *dedicated* cluster (`kafka.enabled=true` in the umbrella chart): the
`kafka` chart in the release namespace, and the topics go there.

The `topics.items` default (`data`) is a placeholder: the server has no
northbound sink yet (<<roadmap>>).

[[deployment-kafka]]
== Kafka chart

A KRaft Kafka cluster (`Kafka` + `KafkaNodePool`, single node by default:
combined controller and broker, replication factor 1) with kafka-exporter and
PodMonitors for the brokers and the exporter. Bootstrap:
`kafka-kafka-bootstrap.<namespace>.svc:9092`. It is used twice: as the shared
cluster (a subchart of the dependencies chart) and as an optional dedicated
cluster of a release (a subchart of the umbrella chart, off by default). It
needs the Strimzi operator watching its namespace; the dependencies chart
installs it watching every namespace.
`podLabels`, `podAnnotations`, `nodeSelector`, `tolerations`, `affinity` and
`topologySpreadConstraints` apply to every pod of the cluster (brokers and
controllers, entity operator, exporter) through Strimzi's pod templates;
Strimzi has no `nodeSelector`, so it becomes required node affinity, added to
every term of `affinity`. `metrics.allowList` selects the metric families the
Strimzi Metrics Reporter exports (what the Strimzi Kafka and KRaft dashboards
use); each family costs series per topic or partition. Its PodMonitors (brokers,
topic operator, exporter) add Strimzi's target labels.

[[deployment-deps]]
== Dependencies chart (the platform)

What every release relies on, installed once per cluster, each part a toggle:

* `kube-prometheus-stack` (92.0.0): Prometheus Operator, Prometheus (5 s scrape,
  picks up monitors and rules from every namespace; two days or 5 GB of
  history on a 10 Gi volume of the default storage class, so restarts keep
  it), Grafana on NodePort 30300 with anonymous viewer access and the
  dashboard sidecar, node-exporter with the TCP/UDP counters the dashboards
  need and the `processes` and `tcpstat` collectors. No AIX/macOS dashboards.
  These are lab settings; production values belong in an override file.
* `strimzi-kafka-operator` (1.2.0), watching every namespace.
* `kafka`: the shared Kafka cluster (<<deployment-topics>>, <<deployment-kafka>>).

`deploy/lab/platform.sh` installs it as release `platform` in namespace
`platform` (`PLATFORM_NAMESPACE`, `PLATFORM_RELEASE`), together with the image
registry (<<deployment-registry>>), and waits for the shared Kafka cluster to be Ready. It is
idempotent; extra helm arguments go after `--`. A component whose CRDs the cluster already serves
from another release is left disabled and the existing installation is used;
one that this release installed before stays enabled.

Its own observability, besides kube-prometheus-stack's (Kubernetes, nodes,
CoreDNS, Prometheus, Grafana):

[cols="1,3",options="header"]
|===
| Grafana folder | Dashboards
| Kafka | Strimzi Kafka and Strimzi KRaft (the Strimzi Metrics Reporter versions, matching the Kafka chart's `metricsConfig`), Strimzi Kafka Exporter (topics, partitions, consumer groups), Strimzi Operators (reconciliations, resources, certificates; the cluster and topic operators).
| Nodes | Node Exporter Full (grafana.com 1860): every node-exporter metric, per node. kube-prometheus-stack's Node Exporter / Nodes stays for the short view; its USE Method boards cannot be turned off on their own.
|===

The third-party dashboards are vendored into `deploy/helm/deps/dashboards/<folder>/`
by `deploy/grafana/fetch-dashboards.sh`, pinned by version and SHA-256 (Strimzi
1.2.0, equal to the operator chart; Node Exporter Full revision 45), with
their licences (Apache-2.0) in `dashboards/LICENCES/`. `dashboards.folders`
maps each folder to its Grafana folder (`""` leaves it out). The Strimzi
dashboards filter on the target labels of Strimzi's example monitors
(`strimzi_io_cluster`, `strimzi_io_name`, `kubernetes_pod_name`); the Kafka
chart's PodMonitors set them. `monitoring.strimziOperator` scrapes the cluster
operator.

Panels that stay empty, by design: consumer groups (until something consumes),
Kafka per-topic rates (until a topic has traffic), Strimzi resources the lab
does not use (Connect, MirrorMaker 2, Bridge, users, rebalances), and on Node
Exporter Full interrupts and systemd (collectors left off: thousands of
series, and the host's D-Bus) and sensors the machine lacks.

[[deployment-lab]]
== Lab (k3s)

Two flows deploy the integration chart. Both use the same install step,
`deploy/lab/install.sh`, and differ in what they deploy and where:

[cols="2,3,3",options="header"]
|===
| | Lab (`deploy/lab/up.sh`) | CI deploy test (`ci/deploy-test.sh`, <<ci>>)
| Deploys | A released package: the CSAR (validated first) or a packaged chart. `--source`: the working tree. | The package under test: the integration chart in the workspace's `dist/`.
| Namespace | `{project}` (`LAB_NAMESPACE`) | `{project}-ci` (`CI_DEPLOY_NAMESPACE`)
| Images | Per component (`{project}-server`, `{project}-loadgen`): the CSAR's own if it carries it, else the local Docker image of the chart's `appVersion`; `--source` builds them. | The ones the pipeline built.
| Dashboard | Shipped with the release. | Off; the lab dashboard shows `{project}-ci` through its namespace selector.
| Platform | Installs it if missing (`platform.sh`). | Must be there; never installs cluster-wide components.
| Kafka topics | `{project}.<topic>`; kept by `down.sh` unless `--delete-topics`. | `{project}-ci.<run id>.<topic>`; deleted after a successful run, kept after a failure.
| Lifetime | Stays up; `helm test` at the end. | `helm test`, the `smoke` scenario on Kubernetes, uninstall (`CI_DEPLOY_KEEP=1` keeps it).
|===

[source,sh,subs="attributes+"]
----
deploy/lab/platform.sh                  # registry (registry.sh up) + dependencies chart; once per cluster
deploy/lab/up.sh                        # dist/{project}-<VERSION>.csar into namespace "{project}"
deploy/lab/up.sh <file.csar|chart.tgz>  # another released package
deploy/lab/up.sh --source               # the working tree (needs a release build: ci/run.sh build-release)
deploy/lab/up.sh -- --set kafka.enabled=true    # extra helm arguments after --: here a dedicated Kafka
deploy/lab/down.sh [--namespace N] [--release R] [--delete-topics]
                                        # uninstall one release (topics, namespace, registry, platform stay)
----

`install.sh --chart <dir|.tgz> [--namespace] [--release] [--image-registry]
[--image-tag] [-- <helm args>]` renders the release first and stops if the
cluster does not serve one of the kinds it renders (the platform is missing),
or if the Kafka cluster its topics go to does not exist. Then it installs or
upgrades, and waits for the workloads, a dedicated Kafka cluster and the topics
to be Ready. A chart directory gets its subcharts packaged
first. The image tag defaults to the chart's `appVersion`.

Grafana: `http://localhost:30300/d/{project}-server`.

[[deployment-registry]]
=== Lab registry

The images go through the lab registry `oci-registry.internal.ystre.org:5000` (`IMAGE_REGISTRY`;
the charts' `image.registry` default). `deploy/lab/registry.sh` runs it:

* *Where*: a Deployment on the registry node (the platform node unless moved,
  see below) with the host network, bound to the node's IPv4 address
  only (not loopback, not container bridges). The data lives on that node
  (local-path volume `registry-data`).
* *Name*: under a domain of ours, so it cannot collide with a public name.
  Containerd and Docker resolve it on the host, not through the cluster DNS,
  so every machine needs it: `setup.sh` pins it in `/etc/hosts` (a marked
  block), or, with `--dns`, relies on a DNS record (an `A` record to the
  registry node, in the domain or in the LAN's DNS) and writes no hosts entry.
  With the record, a move of the registry is a change of one record. Some
  routers drop public DNS answers that carry private addresses (DNS rebinding
  protection): then use the LAN's DNS, or the hosts entry. `--dns` checks that
  the name resolves to the registry node, and leaves `/etc/hosts` as it was
  otherwise.
* *TLS*: 1.3 only. The certificate (ECDSA P-256, one year, `serverAuth`,
  SAN `oci-registry.internal.ystre.org`) comes from a lab CA (ten years, path
  length 0) that is *name-constrained* to that name: a machine that trusts it
  trusts no other name. The CA is installed only where the registry is used:
  `/etc/docker/certs.d/oci-registry.internal.ystre.org:5000/` for Docker,
  `/etc/rancher/k3s/registries.yaml` for containerd; never in the system
  trust store.
* *Authentication*: HTTP basic (bcrypt htpasswd) for every request, pulls
  included. Two accounts: `push` for `docker login` on the machines that
  publish, `pull` for the nodes' containerd. The registry's htpasswd mode does
  not tell them apart in what they may do; they are separate so that the
  credential spread to every node rotates on its own.
* *Pod*: non-root (65532), read-only root filesystem, no capabilities,
  `RuntimeDefault` seccomp, no service account token; an init container with
  only `CHOWN` hands an older root-owned data directory over. Images pinned
  (`registry:3.0.0`, `busybox:1.37.0`).
* *Secrets*: generated on the control-plane machine in
  `~/.local/state/{project}-lab/registry` (`LAB_STATE_DIR`, owner-only): CA
  key, registry key, passwords, htpasswd. The cluster holds the registry's
  share only (Secrets `registry-tls`, `registry-auth`). Back the directory
  up: without the CA key, every machine needs a new bundle.

[source,sh]
----
deploy/lab/registry.sh up                    # CA, credentials, certificate (renewed 30 days ahead), deployment
deploy/lab/registry.sh node-config <dir>     # setup bundle of a machine: CA, pull credentials, setup.sh
sudo <dir>/setup.sh                          # on that machine: /etc/hosts, Docker CA, k3s registries.yaml
deploy/lab/registry.sh login                 # docker login (push account)
deploy/lab/registry.sh check                 # name, TLS, authentication, Docker trust and login
deploy/lab/registry.sh status                # certificate validity, the node, the pod
deploy/lab/registry.sh move <node>           # run it on another node; deletes its images
----

`platform.sh` runs `registry.sh up` every time, so the certificate is renewed
before it expires (the pod rolls over when it, the htpasswd file or the HTTP
secret changes). `up.sh` stops early when `registry.sh check` fails.

First time on the control-plane machine (it is a node too, and the one that
pushes):

[source,sh]
----
deploy/lab/registry.sh up
deploy/lab/registry.sh node-config ~/lab-bundle-$(hostname)
sudo ~/lab-bundle-$(hostname)/setup.sh       # restarts k3s once to load registries.yaml; pods keep running
deploy/lab/registry.sh login
deploy/lab/registry.sh check
----

`setup.sh` runs as root on the target, needs no checkout, and is idempotent.
It writes a marked block into `/etc/hosts` (none with `--dns`), and refuses to touch an existing
`registries.yaml` that it did not write (it prints the block to merge by hand
instead). A bundle holds the pull password (a join bundle also the cluster
token): keep it private and delete it once used.

Rotation::
  certificate: automatic (`registry.sh up`); nothing to do on the machines,
  they trust the CA. Pull password: delete `pull.password`, `registry.sh up`,
  then a new bundle and `setup.sh` on every node. Push password: the same with
  `push.password`, then `registry.sh login`. CA (every ten years, or if its key
  leaks): move the state directory aside, `registry.sh up`, new bundles
  everywhere.

Moving the registry::
  `registry.sh move <node>` runs it on another node of the cluster. The data volume is
  local to the old node and is deleted with the images in it; push them again
  (`up.sh --source`). The name, the certificate and the passwords stay, so the
  machines keep trusting it; only the address changes. With a DNS record,
  change the record; with hosts entries, a new bundle and `setup.sh` on every
  machine. The registry node is recorded in the state directory (`node`).

Limits:: the registry is reachable from the whole LAN (authenticated); limit
  port 5000 to the lab's machines in the host firewall if the network is
  shared. `docker login` stores the password base64-encoded in
  `~/.docker/config.json` unless a credential helper is configured; the CI
  build container (`ci/in-container.sh`) reads that file and cannot use a
  helper. The registry node's address must stay fixed (a DHCP reservation):
  the hosts entries or the DNS record hold it. IPv4 only: the registry binds
  the node's IPv4 address, also on a dual-stack node.

[[deployment-nodes]]
=== Multi-node lab: load generator nodes

The lab runs on one k3s node; more machines (a laptop, say) join it as k3s
agents for the load generator, so that load and server do not share CPUs,
caches and the loopback path.

Placement goes by node roles of the lab's own, labels
`node-role.kubernetes.io/<role>=true` (shown under ROLES in `kubectl get nodes`),
never by the cluster's control-plane label: a real cluster's control-plane
nodes are commonly tainted or out of reach, and the two decisions differ. A
label only draws what asks for it; it keeps nothing away, and every node takes
any other workload. The scripts set the labels (a node may not give itself a
`node-role.kubernetes.io/` label):

* *platform* (one node; `nodes.sh platform <node>`, and `platform.sh` gives it
  to the control-plane node on its first run): the platform, every pod of it
  but the per-node agents (node-exporter), through
  `deploy/lab/platform-values.yaml`; the shared Kafka through the Kafka
  chart's `nodeSelector` (node affinity in Strimzi's pod templates). Its
  volumes stay on the node they were created on, and a laptop may sleep. By
  default also the server (`up.sh --server-nodes`: `loadgen` for the load
  generator nodes, `any` for the scheduler's choice; `server.placement.nodes`)
  and, on its first `up`, the registry, which then stays on its node
  (<<deployment-registry>>).
* *loadgen* (`nodes.sh loadgen <node>`, not the platform node): the load
  generator, when a run asks for it (`placement.dedicatedNodes=true`,
  `run.py --loadgen-nodes`). An earlier layout tainted these nodes;
  `nodes.sh loadgen` removes that taint.

Moving the platform label does not move the platform's data: Prometheus's and
the shared Kafka's volumes stay on the old node, and `platform.sh` stops, naming
them, until the label moves back or they are deleted with their data
(<<tech-debt>>).

[source,sh]
----
deploy/lab/nodes.sh join ~/lab-join-laptop   # bundle: registry setup + k3s join (reads the k3s token with sudo)
scp -r ~/lab-join-laptop laptop:             # a trusted channel: the bundle holds the join token
ssh -t laptop sudo ./lab-join-laptop/setup.sh [--node-ip <LAN address>] [--dns]
#   registry trust and credentials first, then the k3s agent (cluster's version)
deploy/lab/nodes.sh loadgen <node>   # label it as a load generator node
deploy/lab/nodes.sh platform <node>  # make it the platform node (asks first: the data stays behind)
deploy/lab/nodes.sh status           # nodes, roles, taints
python3 -I tools/bench/run.py --target k8s --scenario smoke --loadgen-nodes
deploy/lab/nodes.sh remove <node>    # drain and delete it; then k3s-agent-uninstall.sh on the node
----

The new node must reach the control plane on 6443/tcp, and the nodes each
other on 8472/udp (flannel VXLAN) and 10250/tcp (kubelet, for logs and exec).
On a machine with several interfaces (Wi-Fi and Ethernet, VPN), pin the
address with `--node-ip` (and `--flannel-iface`). A node that sleeps or leaves
the network goes `NotReady`; a run scheduled there fails, the rest of the lab
is unaffected.

The node pulls from the lab registry like every other (<<deployment-registry>>):
the join bundle's `setup.sh` adds the name, the CA and the pull credentials
before the agent starts.

Measurements across machines include the network between them (Wi-Fi in the
laptop case): latency figures from such runs compare only with runs on the
same pair of nodes and link (<<bench-host>>).

== Dashboard

`deploy/grafana/build_dashboard.py` generates the dashboard
(`deploy/helm/server/dashboards/server.json`) from the metrics contract. It
has variables for namespace, server pod and reactor, and load-run annotations.

[cols="1,4",options="header"]
|===
| Row | Panels
| Overview | Messages/s and bytes/s in and out, connections, accepts/s, RTT p99, server CPU cores, CPU per message, build/backend, reactors, integrity/protocol/rejection/UDP-drop counters (red if any), generator saturation.
| Pipeline | Generator sent → server received → server replied → generator received; bytes; messages by type and by reactor (imbalance).
| Latency | RTT quantiles and heatmap (generator), handler time per receive, message age, generator send lag.
| Connections | Open by transport, accepts/closes/rejections by reason, errors.
| Reactors | Utilisation, loop iterations, messages per iteration, syscalls by operation, io_uring batching, buffer ring exhaustion, zero-copy results, container CPU and throttling.
| Backpressure and memory | Backpressure events and time, send queues, buffers by kind, container memory.
| UDP | Datagrams, server drops, kernel UDP errors.
| Node | Softirq per core, NIC packets, TCP retransmits and listen overflows, NIC drops.
|===

In Phase 1, only build info, connections, bytes, messages and protocol errors
have data; the other panels are there to review layout and names.
